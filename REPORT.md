# Итоговый аналитический отчет (Лабораторная работа №1)

## 1. Резюме (Executive Summary)
В рамках лабораторной работы был спроектирован процесс разработки микросервиса «Расчет корзины и скидок». Выбрана СУБД, настроена ветвящаяся модель репозитория с защитой базовой линии, внедрен автоматический контроль качества кода (CI/CD на базе GitHub Actions и flake8), проведен анализ legacy-кода с построением UML-диаграммы и составлен план code-review.

## 2. Сравнительный анализ технологий
### 2.1. Матрица принятия решений

### 2.2. Расчет и обоснование выбора
Формула: `Оценка = Сумма (Вес * Балл)`
- **PostgreSQL:** `0.35*5 + 0.25*5 + 0.20*4 + 0.10*3 + 0.10*5 = 4.60`
- **MongoDB:** `0.35*3 + 0.25*2 + 0.20*4 + 0.10*5 + 0.10*4 = 3.25`

**Обоснование:** Победитель — **PostgreSQL** (4.60 против 3.25). Для микросервиса лояльности критически важна строгая целостность финансовых транзакций и бонусных счетов, которую гарантирует полная поддержка ACID.

## 5. Обратное проектирование и планирование ревью
### 5.1. Анализ алгоритма
![UML Diagram](https://github.com/blob/feature/review-plan/docs/uml_diagram.png?raw=true)

Выявленные «запахи кода» (Code Smells) в legacy-фрагменте:
1. **Магические числа (Magic Numbers):** `15000`, `0.85`, `500`, `0.90`, `0.97`, `0.93`, `0.70` зашиты прямо в код без констант.
2. **Отсутствие валидации:** не проверяются отрицательные суммы корзины и некорректные типы данных.
3. **Жесткая привязка промокодов (Hardcode):** названия акций `"SUMMER"` и `"VIP"` зашиты в условия `if/elif`, что требует правки кода при каждой новой акции.

### 5.2. План code-review
Ревью проводится перед слиянием любой feature-ветки в `develop` с обязательным аппрувом от Code Owner. Ключевые критерии: отсутствие магических чисел, валидация входных данных и покрытие тестами > 80%. При спорах свыше 24 часов вопрос эскалируется на Tech Lead.
Ссылка на открытый Pull Request: https://github.com/pull/3
